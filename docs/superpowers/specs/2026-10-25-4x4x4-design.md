# 4×4×4 tic tac toe: design

Date: 2026-10-25. Status: approved by the user on 2026-10-25.

## Intent

Replace the current 3×3 game with 4×4×4 tic tac toe (sometimes called Qubic). It stays a casual two-player game on one phone. The point is the 3D board: players see the whole cube, turn it with a finger, and play directly on it. Lines that cross layers should be easy to see, which is the hard part of 4×4×4 on a flat screen.

## Goals

- Two players, same device, taking turns. X always moves first.
- A second mode: one player against the computer (added by the user on 2026-10-25; details in "Play vs computer" below).
- A 4×4×4 board (64 cells). A player wins with 4 of their pieces in any straight line: rows, columns and diagonals within a layer, vertical pillars, diagonals across any vertical slice, and the 4 corner-to-corner space diagonals. That is 76 lines in total. A full board with no line is a draw.
- The only board view is a rotatable 3D cube built from 64 small cubes. Players do everything on the cube: rotate it, pick a layer, select a cell, confirm the move.
- It works the same in a phone browser, as an installed PWA, and in the Android WebView app, fully offline.

## Non-goals

- No online play, score keeping across games, undo or move history.
- No flat 2D layer grids as a second view or input method. These were explored in mockups and rejected in favour of cube-only.
- Keeping the 3×3 game. This replaces it; there is no mode switch.
- No new app icon for now; the existing `icon.png` stays (my call).

## Anti-goals (would count as failure even if it technically works)

- Hard to put a piece where you meant to: mis-taps that place on the wrong cell or layer.
- A board you have to scroll to see, or that doesn't fit a normal phone screen in portrait.
- Adding dependencies, a build step, network requests or CDN assets (CLAUDE.md rules).

## Constraints

- Plain HTML/CSS/JS in the single root `index.html`, no frameworks or libraries. 3D is drawn by hand on a 2D `<canvas>` (the prototype shows this is enough), not WebGL or three.js.
- Must run from `file://` inside the Android WebView (`file:///android_asset/index.html`) and offline as a PWA.
- Touch-first: no hover-only behaviour. Must also work with a mouse on desktop.
- Dark theme as today (`#111` page background).
- Must fit a portrait phone viewport of about 360×640 CSS px without scrolling, and scale up sensibly on larger screens.

## The design (decided with the user)

A working prototype is in `docs/superpowers/specs/2026-10-25-4x4x4-prototype.html`. It is a fragment that was shown inside a mockup frame, so it has no `<html>`/`<head>` and uses a fixed 340 px phone frame, but its game logic, rendering and interaction are what was approved. Use it as the reference for look and behaviour; it is not production code. Its "Demo position" button and explanatory text are mockup-only and must not ship.

### Screen

Top to bottom: title, mode label (see "Picking the mode"), status line, the cube canvas (most of the screen), a short hint line, a "New game" button. Nothing else, apart from the "New game" sheet described under "Play vs computer".

### The cube

- 64 small cubes on an even lattice: equal spacing in all three directions, so it reads as one 4×4×4 cube (the "C1" option; the layers-pulled-apart variant was rejected).
- Layer 1 is the top layer, layer 4 the bottom.
- Empty cells are faint, see-through glass cubes (low-alpha faces, thin light edges).
- X is a solid blue cube, O a solid red cube (about 85% opacity, shaded per face so they look 3D). Prototype colours: X `rgb(60,150,255)`, O `rgb(255,70,70)`.
- Rendering uses perspective projection, with cubes drawn back to front and faces back to front within each cube.

### Rotation

- Drag anywhere on the cube to rotate it: horizontal drag turns it around the vertical axis, vertical drag tilts it. The tilt is clamped so the cube can't flip upside down (prototype: ±1.3 rad).
- A press that moves less than about 8 px counts as a tap, not a drag.

### Choosing a layer

- Four round number badges (1 to 4) sit in a column at the left edge of the canvas. Each badge follows its layer's on-screen height as the cube rotates. Badges are pushed apart so they never overlap and stay tappable.
- Tapping a badge makes that layer active. The active badge is filled light; the others are dark.
- On the active layer, empty cubes get brighter outlines and a little more fill. Empty cubes on other layers fade further. Placed pieces always stay solid, whatever the layer.
- Layer 1 is active when a game starts.

### Placing a piece (two taps)

1. Tap an empty cube on the active layer to select it. It shows as a see-through cube in the current player's colour with dashed outlines, and the status reads "X: tap again to place" (or O).
2. Tap the same cube again to place the piece. The turn passes to the other player.

- Tapping a different empty cube on the active layer moves the selection.
- Tapping empty space, or any layer badge, clears the selection.
- Rotating keeps the selection.
- Cubes on other layers, and already-filled cubes, ignore taps.
- Hit testing: cubes overlap on screen in the even lattice, so "topmost cube under the finger" picks the wrong one. The tap goes to the active-layer empty cube whose projected centre is nearest the tap point, within a radius of about the cube's on-screen size. Cube centres within one layer stay well apart on screen, so this was reliable in testing.

### Status line

- Normal: "X's turn · layer 2".
- With a selection: "X: tap again to place".
- End: "X wins", "O wins" or "Draw".

### Last move and game end

- The most recently placed piece has a white outline.
- On a win, the four winning cubes get green outlines and a green line is drawn through their centres. The game stops accepting moves; rotation still works. A full board with no line shows "Draw".
- Starting a new game (from the "New game" sheet) clears the board, sets X to move, selects layer 1 and clears any selection. The rotation angle is kept (my call).

## Play vs computer

Four modes (decided with the user): two players on one phone, or one player against the computer at easy, medium or hard.

The computer does not need to play perfectly. 4×4×4 is solved (the first player can force a win; Patashnik 1980, later confirmed by Allis), but perfect play would need a huge stored table of winning moves and would not be fun. The levels are built from simple pieces instead:

- Easy: wins if it can, blocks the opponent's three-in-a-row, otherwise picks a reasonable cell with some randomness. Casual players should usually beat it.
- Medium: also creates and blocks double threats (two open lines that each need one more piece, so only one can be blocked).
- Hard: also looks a few moves ahead for forcing sequences, where each move makes three in a row and leaves the opponent only one block. It should beat most people, but it is not a perfect player.

Every level must move quickly on a phone, with no visible freeze.

Against the computer, the player is always X and moves first (decided with the user). The computer plays O.

While the computer chooses, the status reads "Computer is thinking…" and the board ignores taps. There is a short pause (about half a second, even when the move is found instantly) so the move doesn't feel jarring. The computer's move gets the normal last-move outline. Rotation keeps working while it thinks. (My call.)

### Picking the mode (decided with the user: the "New game" list)

- The main screen has no mode controls. "New game" opens a bottom sheet listing the four modes: "2 players" (same phone), "vs Computer: Easy", "vs Computer: Medium", "vs Computer: Hard". The last-played mode is marked.
- Choosing a mode starts a new game in that mode straight away. Tapping outside the sheet closes it with nothing changed, so the sheet doubles as the "abandon this game?" confirmation.
- A small, dim mode label sits under the title: "2 players" or "vs Computer · Medium". The status line itself stays short (see below) so it fits on one line at 360 px. (My call.)
- The last-chosen mode is saved in `localStorage` (wrapped in try/catch; if storage is unavailable the game just doesn't remember). On a later launch the game starts directly in that mode. On the very first launch, with nothing saved, the sheet opens automatically. (My call.)
- A mockup is in the brainstorm session (`.superpowers/`, not committed); the description above is the full spec.

### Status text against the computer

"Your turn · layer 2", "You: tap again to place", "Computer is thinking…", "You win", "Computer wins", "Draw". In 2-player mode the status stays as described above ("X's turn · layer 2", "X wins"). (My call.)

## Housekeeping that comes with the change

- `index.html`: replace the 3×3 game entirely. Title "Tic Tac Toe 4×4×4" (my call).
- `manifest.json`: update `name` to match. `short_name` can stay.
- `sw.js`: bump `CACHE` (`ttt-v1` → `ttt-v2`) so installed PWAs pick up the new game.
- `android/src/.../MainActivity.java`: enable DOM storage (`setDomStorageEnabled(true)`). Android WebView turns `localStorage` off by default, so without this the saved mode is lost.
- `android/AndroidManifest.xml`: bump `versionCode` to 2 and `versionName` to 2.0 (my call). The package ID stays `com.andrej.tictactoe`.
- Rebuild `tic-tac-toe.apk` with `android/build.sh`. This needs the Android SDK, which is not installed on the dev Mac. If the SDK isn't available, the web version can ship first and the APK rebuild becomes a follow-up. A rebuild on a new machine creates a new debug key, so the phone must uninstall the old app first (already noted in CLAUDE.md).
- Update `README.md` and `CLAUDE.md`: describe the new game, and remove the "Direction" note from CLAUDE.md.

## Left to the builder

- Canvas sizing: fill the available width and height within the screen layout, handle device pixel ratio, and re-layout on resize or orientation change. The prototype is fixed at 316×470.
- Exact sizes, spacing, alpha values, lighting and badge size, keeping the look of the prototype. Small-cube size should stay at least as large as the prototype's (half-size 0.32 of the lattice spacing) for tap accuracy.
- Code structure inside `index.html`, and how to test. CLAUDE.md says there are no automated tests; a small automated check of the win-line count (76) and the tap rules is welcome if it adds no dependencies to the shipped page. The prototype was verified with scripted taps in headless Chrome.
- Whether the initial rotation angle is the prototype's (yaw −0.6, pitch 0.45) or something similar.
- The tilt limit stays at ±1.3 rad even though a side-on view makes the active layer's cubes overlap on screen; the two-tap flow means a wrong pick is visible before anything is placed.
- Build order: the 2-player cube game first, then the computer levels and the mode sheet on top. Easy, then medium, then hard. (My call.)
